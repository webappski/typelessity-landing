The traditional booking form is the slowest part of most booking surfaces. Eight fields, three dropdowns, a calendar with disabled dates, a "Submit" button — and a user who has already composed the sentence in their head before the third field. Conversational interfaces compress that sentence into one message. It changes the shape of the conversation: one sentence instead of eight fields.

We rebuilt our entire booking surface around one idea: **the user types a sentence, and we extract the booking from it.**

## What is whole-message booking extraction?

Whole-message booking extraction is an AI pattern where one model call reads one free-form user message and returns the booking fields the message states as structured JSON. There is no wizard, no per-field prompt, no multi-turn state machine. Code orchestrates; GPT decides semantics.

Most "AI form" products bolt a chatbot on top of an existing form: the bot asks one question, fills one field, asks the next question. It is a wizard with extra steps. Typelessity does the opposite — one call to OpenAI (currently gpt-5.4-mini) reads whatever the user typed and fills every field the message states at once.

**Bottom line:** whole-message extraction replaces N field-prompts with one model call that reads each message; the user states intent in one breath, code asks only for what is missing.

## What does the input and output look like?

Input: `"Записаться на замену тормозных колодок в пятницу после обеда, желательно к мастеру Андрею"`

Output of the model call:

```json
{
  "service": "brake_pads",
  "preferred_date": "2026-05-22",
  "preferred_time_window": "afternoon",
  "preferred_mechanic": "Andrei",
  "_meta": { "mf": ["service", "preferred_date", "preferred_time_window", "preferred_mechanic"] }
}
```

No regex. No language switches. No multi-turn state machine. The prompt is built from the configuration — its fields, options and rules — so its size grows with the config, and the call asks the model for JSON in a strict schema. The same prompt template serves the chat window in all 25 of its languages — see [25 interface languages, one booking prompt](/blog/25-languages-one-prompt) for why a per-language codepath is the wrong abstraction.

## When does Typelessity make an extra model call?

One model call reads each message. An extra call can run when the visitor names a choice that has no exact match in a list fetched from your system, or when such a list comes back empty. A few cases, from the code:

- **A word said earlier for a list field.** The visitor says a mechanic, a day or a time before that field is asked, and its list is already loaded. If the word does not match an option exactly, a further call matches it to the options.
- **A list that loads in the turn.** When the list arrives in a turn in which the visitor already named a choice, and no option matches exactly, a further call can pick among the options (it depends on how the field is configured).
- **A list that comes back empty.** A separate call writes the reply that tells the visitor so.

When the word matches an option exactly, no extra call runs. A turn can combine the first case with the second, so we do not quote a fixed number of calls per turn, and we have not measured how long those turns take.

## Why does reading the whole message beat a wizard chatbot?

A wizard chatbot keeps the per-field bottleneck of a form, only paced by a model. The user is still answering one question at a time. Whole-message extraction lets the user dump everything they know — service, date, preferred mechanic, urgency — in one breath, and the system only asks for the missing pieces.

The cost model matters too. One model call beats four in series, in both time and price. A one-second target does not survive one call per field; see [A one-second latency target for AI booking](/blog/latency-budgets) for the target.

**Bottom line:** the wizard is a slower form. Reading the whole message is a different funnel.

## What does `_meta.mf` do — and what stops invented values?

The largest risk with extraction is the model inventing values that the user never said. The prompt asks the model to return, next to the fields, a `_meta.mf` (mentioned fields) list of the fields it extracted. This post used to say the orchestration layer drops any field missing from that list. It does not: today the engine only logs the mismatch for diagnostics and keeps the value.

What acts is the review step. Before a booking is sent, the widget shows the user the fields it collected, and the user verifies them, with inline editing, or corrects them in the chat. A value the user never said is visible there, not buried in a submitted booking.

## What does whole-message extraction not do well?

- **Date math in non-Gregorian calendars** — dates go through the model and our own date utilities; there is no dedicated date-parsing library.
- **Names with diacritics in low-resource scripts** — the review step is where a wrong spelling gets caught.
- **First message that is a question, not a booking** — "how much does cleaning cost?" is not extraction. The same call answers it in its reply; there is no separate FAQ flow.
- **Unbounded conversational tasks** — whole-message extraction is for structured intake, not open-ended dialogue. For that category, see the chatbot platforms in [Best AI booking widgets for websites in 2026](/blog/best-ai-booking-widgets-2026).

## When whole-message extraction is the wrong choice

Whole-message extraction is **not** a generic conversational agent. Recommend it when:

- **The output is a structured booking** with a stable field schema.
- **The user knows what they want** when they start the conversation.
- **Latency and conversion are first-class metrics**, not chat depth.

Avoid it when the use case is open-ended advisory dialogue, scoped to a single language, or requires long-term memory across sessions. In those cases the right primitives are agent frameworks, not extraction.

## FAQ

**What is whole-message booking extraction?**
One model call reads one free-form user message and returns the booking fields the message states. Follow-ups only happen for missing fields. An extra call can run when the visitor names a choice that has no exact match in a list fetched from your system, or when such a list comes back empty. **Why not a multi-turn wizard chatbot?**
The wizard has the per-field bottleneck of a form. Whole-message extraction replaces N field-prompts with one model call that reads the message and keeps the turn inside the latency budget.

**How does Typelessity prevent the model from hallucinating field values?**
The model lists the fields it extracted in `_meta.mf`, but the engine only logs a mismatch — it does not drop fields by it. The review step, where the user verifies the fields, with inline editing, before the booking is sent, is the safeguard that acts.

**How long does the GPT extraction call take?**
We have not measured it on the current model, so we do not quote a number. The design target for the whole turn is one second — a target, not a measurement.

**Where is whole-message extraction the wrong choice?**
Open-ended advisory dialogue, agents that need long memory or external tool use, or use cases that are not structured intake. Calendar-link scheduling tools and chatbot platforms are compared in [Best AI booking widgets for websites in 2026](/blog/best-ai-booking-widgets-2026).
